Изменения относятся к 22 файлам программы и её документации; исходный состав — 19 изменённых и 3 новых. Адресный список и контрольные суммы сверяются перед commit; `git add .` не используется.

Проверены статусы параллельных чатов: «Построение мнемосхемы» — idle, последний ход completed; «Подготовить схему теплообменника» и «Создать макет веб-HMI теплообменника» — notLoaded, последние ходы completed. Перед записью Git статус чатов и неизменность состава проверяются ещё раз.

Принятые решения закрыты: сохранение аварии перегрева до своего условия снятия; обязательный останов незавершённого Пуска при критической водяной причине; восстановление отдельного запроса теплоотвода после reboot до прежнего условия снятия. Два последних разрешения не утверждают реакции в инженерных тестах и не назначают физический интерфейс. Подробности и пределы реализации ниже.

## Утверждённые основания и реализация

Пользователь ответил «Сохранять до условия снятия» на восстановление уже зафиксированного перегрева воды после reboot при новых 88 °C. На критическую водяную причину во время незавершённого Пуска ответил «Прерывать указанным остановом». Эти ответы дополняют D-023/D-024; остальные пороги, гистерезис, гидравлические разрешения и общий порядок останова сохранены.

| Сценарий | Поведение модели |
|---|---|
| Перегрев воды или потеря обеих подач в STARTING | После диагностики воды, до шага основной программы, запускается существующий обязательный останов ШБ → ШТ. Завершить Пуск в RUNNING в том же цикле нельзя |
| Снятие водяной причины после прерывания | Удаляет только свою аварийную причину; уже принятый останов остаётся обязательным. Автоматического возврата в запуск нет |
| Ожидание ШБ / закрытие ШТ | Сохраняются разрешённые текущие команды циркуляции и прежний порядок останова. Новых пусковых этапов нет. Закрытие ШТ начинается только после нового подтверждения ШБ |
| ШТ закрылся | Прежнее заключительное закрытие рабочего затвора → OFF насосов → окончание останова. Водяной сценарий не заменяет диагностику приводов |
| Повторы / старое окно | Повтор причины не меняет номер процедуры/таймер движения и не подтверждает ШБ. Подтверждение из старого контекста отклоняется |
| Совместное низкое давление | D-149 по-прежнему немедленно снимает команды насосам и открывает затворы. Нормализация давления не отменяет обязательный водяной останов |
| Установившаяся RUNNING | Прежний D-023/D-024: сама водяная причина не останавливает установку |
| Активный инженерный тест | Прежняя явная пауза: новое согласование незавершённого Пуска не распространяется автоматически на тесты |

При OPEN_ST не добавлялась отдельная новая команда положения до ШБ: используется прежняя последовательность обязательного останова, с ранее выданными запросами и собственной диагностикой движения.

## Восстановление перегрева и запроса теплоотвода

В читаемом имитируемом снимке переносится уже установленная авария `overheat`. Старые измерения не восстанавливаются; при отсутствии всех новых температур доказательства снятия нет. Новые 88 или ровно 86 °C сохраняют аварию без повторных 3 с; когда максимум доступных достоверных водяных каналов ниже 86 °C, снимается только WATER_OVERHEAT. Один пригодный канал может доказать снятие по D-024/D-152; это не заменяет контроль подачи и остальные разрешения.

Незавершённые таймеры перегрева, теплоотвода и ΔT не переносятся. Непрочитанный снимок не объявляется известным сохранённым состоянием. Повторный reboot не превращает неизвестность в достоверность. Новый экземпляр Simulation не получает память предыдущего процесса.

В читаемом снимке восстанавливается и `thermalRemoval`. Текущий `heatRemoval.request` заново вычисляется общей водяной защитой и выдаётся единственным отправителем Protection уже на стадии WAIT_INPUTS. Это отдельный виртуальный запрос: он не ждёт подтверждения STOP ПЧ/ШТ и не создаёт таких подтверждений. Остальные механизмы проходят прежнее восстановление по новым данным; из RUNNING/STARTING/STOPPING — только обязательный останов с новым ШБ и отдельным «Продолжить».

Пока нет новых пригодных подач, по D-024 запрос принудительный независимо от сохранённого температурного состояния. Восстановление одного датчика подачи снимает только эту причину. При сохранённом `thermalRemoval=true` новые 82 или ровно 80 °C продолжают запрос, ниже 80 снимают. При сохранённом false и новых 82 °C запрос снимается после восстановления подачи; вынужденный запрос из-за отсутствия измерений не превращается в температурную защёлку. Уставки берутся из того же читаемого снимка. Незавершённые 3 с начинаются заново по новым измерениям; простой не засчитывается.

`recoveryPending=true` теперь означает непрочитанный снимок. В этом случае сохраняется coverageGap, новые выходы не выдаются, HMI не показывает вымышленное OFF. Повторный reboot не снимает неизвестность. `savedThermalRemoval` — история прочитанного снимка, отдельно от текущего запроса и физической обратной связи.

## Закрытое уточнение — 15.11.2026

После разъяснения по D-023/D-044 пользователь разрешил запрос после перезагрузки. Функция означает третью скорость местных тепловентиляторов и предусмотренный запрос котельной на другие группы. Согласован конкретный случай 87 → 82 °C → reboot → новые 82 °C: сохранить запрос до всех доступных исправных ниже прежнего порога отключения (80 °C по умолчанию), без повторных 3 с. Это отдельное согласование, дополняющее сохранение аварии перегрева. В модели только `heatRemoval.request`; физические выходы, доставка запроса и работа вентиляторов не подтверждаются.
